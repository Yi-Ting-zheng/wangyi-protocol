# MA-008 — Per-Declaration Provenance & Model-Signature Registration Gate

> **Protocol:** Wangyi Protocol v2.0-draft　**Type:** BLOCKING verdict gate
> **Truth level:** `DEFINITION` (rule text); gate effects are `EMPIRICAL`.
> **Normative schema:** [schema/provenance_schema.yaml](../schema/provenance_schema.yaml)
> **Origin incident:** the systemic provenance gap in every large AI-generated
> formal corpus surveyed to date (OAI ~121,700-file corpus, Ghys SHEAF, …):
> release notes state only "AI-assisted" at project level, with no
> per-declaration record of which proofs are AI drafts, which are human
> rewrites, and which are pure-human — leaving the production narrative
> permanently re-writable after publication.

## 1. Motivation: the provenance defect

Current AI formalization projects record **only the final Lean source**. They
do **not**, for any individual proof or lemma, distinguish:

- AI-generated draft, subsequently heavily edited by a human;
- AI-suggested lemma name / proof outline, code written entirely by hand;
- entirely human-written, no model involvement;
- human-completed proof with only a few tactic lines tuned by a model;
- AI-generated fully-compiling proof, human acting as auditor only.

The consequence is a **narrative-inflation channel** that is structurally
uncheckable after the fact: a project can be released as "AI-assisted", and
years later re-described as "AI independently proved the conjecture", because
no cryptographic record of the production chain was ever pinned.

MA-008 closes this by making **per-declaration provenance** a first-class
audit artifact, hash-locked and append-only.

## 2. Core principle: provenance is NOT a truth claim

> **Provenance records *how* an artifact was produced. It says nothing
> about *whether* it is true.**

This is a hard discipline, not a suggestion:

1. **Source annotation ≠ truth certification.** A lemma produced by a model is
   not thereby credible; a lemma written by a human is not thereby trusted.
   Both must still pass WP-L1 (syntax), WP-L2 (axiom dependency + ontology
   binding + gap registration), and WP-L3 (auditor self-certification) in full.
2. **Provenance signatures carry no credibility weight.** `model_signature`,
   `model_version`, and `contribution_type` are descriptive fields only. They
   MUST NOT be used to upgrade a truth grade, to relax an audit gate, or to
   describe a result as "model-verified".
3. **The provenance ledger itself is subject to WP-L1/L2/L3.** A provenance
   record that cannot be reconciled with the source it describes is a
   `PROVENANCE_MISMATCH` finding, not a PASS.

This separation is what makes MA-008 compatible with §2 (Truth Grading):
provenance lives on the **production** axis; truth grades live on the
**mathematical** axis. The two MUST NOT be conflated in any report.

## 3. Record model: per-declaration granularity

### 3.1 The per-declaration rule (BLOCKING)

Provenance MUST be registered **per declaration** — one record per lemma,
theorem, conditional theorem, conjecture, or gap skeleton.

**Project-level blanket statements are FORBIDDEN.** A line such as
"this project was produced with AI assistance" in a project README, with no
per-declaration breakdown, is a `PROVENANCE_INSUFFICIENT` BLOCKING finding.
The granularity requirement exists precisely because a project may contain a
mixture: 3 lemmas as AI drafts, 12 pure-human, 1 AI-complete. Collapsing them
into one label destroys the information the gate is designed to preserve.

### 3.2 What counts as a declaration

Every `theorem` / `lemma` / `axiom` / `conjecture`-position declaration that
appears in the audited corpus's declaration inventory (see spec §3.2(3) gap
registration; the ledger semantics live in the **GAP ledger**, see glossary)
MUST have exactly one provenance record. Declarations that exist only as
`sorry`-bearing skeletons are registered as `GAP-SKELETON` — this is the
honest label, and it MUST be registered rather than silently omitted.

## 4. Field definitions

A provenance record is a YAML object conforming to
[../schema/provenance_schema.yaml](../schema/provenance_schema.yaml). Fields:

| Field | Type | Required | Meaning |
|---|---|---|---|
| `artifact_id` | string | YES | Project-unique identifier. MUST be stable across revisions of the *same* declaration (renaming the declaration invalidates the id and requires a new record). Recommended form: `<project>-<n>[_<stage>]`, e.g. `GT001_step2_algIndep`. |
| `artifact_type` | enum | YES | See §5.1. |
| `statement_hash_sha256` | string (hex, 64) | YES | SHA-256 of the **proposition statement text** (declaration type span), normalized per the exact algorithm in §4.2. Changing the statement changes the hash → new record. |
| `proof_hash_sha256` | string (hex, 64) | YES | SHA-256 of the **proof body** (the `by …` / `:= …` term span, or `sorry` for skeletons), byte-exact per §4.2. For `CONJECTURE` this is the hash of the empty string (no proof exists) — the field stays present so schema shape is uniform. |
| `provenance` | array of stage objects | YES | The production chain, in chronological order. Append-only: each stage is a production event. See §4.1. |
| `modification_log` | array of modification objects | NO (RECOMMENDED) | The human-edit chain from AI draft to final proof. See §7. Absence is a `PROVENANCE_INCOMPLETE` warning, not a block. |

### 4.1 `provenance` — production stages

Each stage object:

| Field | Type | Meaning |
|---|---|---|
| `stage` | enum | `draft` / `refactor` / `final_tweak`. The production phase this stage belongs to. |
| `model_family` | string | Model family, e.g. `InternLM2`, `GPT-4o`, `Claude-3-5-Sonnet`. Free text but SHOULD use the vendor's published family name. |
| `model_version` | string | Specific model version, e.g. `InternLM2-72B-Chat`, `gpt-4o-2024-08-06`. |
| `model_signature` | string | **Model weight/release fingerprint.** For open-weight models: the SHA-256 of the weight checkpoint (or the published checkpoint manifest hash). For closed-source models: the official release identifier **plus** the release digest published by the provider (e.g. `gpt-4o-2024-08-06` + provider release note hash). This field permanently pins *which exact model* produced this draft, so that later model iterations cannot retroactively alter the record. |
| `contribution_type` | enum | **The single most important field** — see §5.2. |
| `timestamp` | string (ISO 8601) | Production timestamp of this stage, with timezone offset. |
| `auditor` | string | Identity of the L3 auditor who adjudicated this stage (human or agent name). |
| `audit_verdict` | string | The WP-L1/L2/L3 verdict reached at this stage, e.g. `PASS_L2`, `BLOCK_条件A`, `INCONCLUSIVE`. Records the audit state *at production time*. Schema v1.3 introduces `audit_verdict_enum` as a **first-draft disclosure set** (pass-the-L-level tokens `PASS_L1…L3` / `BLOCK_L1…L3` / `INCONCLUSIVE`, plus gate-branch composite tokens such as MA-007's `BLOCK_条件A` quoted verbatim). P3 still does NOT enforce it: a value outside the draft set is disclosed on the warn channel, never a BLOCK; the set is deliberately left un-closed until one round of real-manifest observation plus a four-axis control group passes (TP-MA008-2 #4). |
| `execution_environment` | enum (since schema v1.1) | The **conditions of generation** — `internal_cluster` / `external_api` / `local_runtime` (§5.4). Records *where and under which serving regime* this stage was produced. Mixed environments within one stage are FORBIDDEN — split into separate stages. Absence in v1.0-manifests is disclosed per item by P9 (warn). |
| `cost_ledger_ref` | string (hex, 64) | Optional. Hash pointer into the **compute-chain billing ledger slice** covering this stage. Token consumption, cache policy and quota figures are self-attested quantities (internal-cluster metering has no external counterparty to audit them) and MUST live in the billing ledger — never in this manifest. Pointer/scope/conflict rules: §9.1. |

A record MUST contain at least one stage. Multiple stages are the normal case
for AI-assisted work (draft → refactor → final_tweak). On a `HUMAN_FULL`
stage the three model-identity fields (`model_family`, `model_version`,
`model_signature`) MUST be the **empty string** — schema shape stays uniform,
and P3 treats emptiness as valid *only* on `HUMAN_FULL` stages (§8.2).

### 4.2 Hash normalization (normative appendix)

`statement_hash_sha256` and `proof_hash_sha256` are computed as follows. The
algorithm is pinned so that two conforming implementations agree
byte-for-byte; it mirrors the reference implementation exactly.

**Statement span** — the exact source slice from the depth-0 `:` that
separates the binders from the type, through the end of the declaration
head (immediately before the proof-opening `:=`); the leading `:` is part
of the span.

**Statement normalization** (applied to the statement span):

1. collapse every run of whitespace (spaces, tabs, newlines) to a single
   ASCII space;
2. strip leading/trailing space;
3. encode UTF-8, then SHA-256. (No Unicode NFC folding, no comment removal
   — anything else changes hashes and MUST NOT be applied.)

**Proof span** — the exact source slice from the character after the
depth-0 `:=` through the end of the declaration, with the trailing
whitespace stripped. The proof hash is computed over this span
**byte-exact** (no whitespace collapsing): proof indentation is
meaningful signal for tactic structure, and normalization here would erase
distinguishable states in the modification chain.

**Degenerate cases:**

- `CONJECTURE` records: `proof_hash_sha256` =
  `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`
  (SHA-256 of the empty string).
- `GAP-SKELETON` records: proof span is the literal `sorry`.
- CRLF/O-CR cleanups, U+FFFD-damaged corpora, binder-defaults
  (`(x : T := e)`) that defeat depth-0 `:=` location: the declaration is
  **unparseable** — it enters the P0 finding class, never a guessed hash.

**Conformance vectors:** examples/ma008_hash_vectors/ ships input spans +
expected hashes; a second implementation that disagrees on any vector is
not conformant (test vectors are data, not code — the repository still
ships no executable scripts).

## 5. Enumerations (normative, fixed)

### 5.1 `artifact_type`

| Value | Meaning |
|---|---|
| `LEMMA` | Auxiliary lemma serving the main proof chain. |
| `THEOREM` | Unconditional theorem: zero external axioms, zero top-level `sorry`. |
| `THEOREM-COND` | Conditional theorem: depends **only** on whitelisted, registered external hypotheses (e.g. a `SchanuelAt` instance axiom). |
| `CONJECTURE` | Conjecture: statement only, no proof. |
| `GAP-SKELETON` | Gap skeleton: statement + `sorry` placeholder. An explicit攻坚 target, registered in the GAP ledger. Honest by design — a skeleton that is *not* registered is a `GAP_UNREGISTERED` BLOCK. |

### 5.2 `contribution_type` (the anti-inflation field)

This enumeration exists for one reason: **to make narrative inflation
machine-detectable.** The values are mutually exclusive and exhaustive;
exactly one MUST be chosen per stage. Vague labels such as "AI-assisted" are
NOT permitted and are a `PROVENANCE_INSUFFICIENT` BLOCK.

| Value | Definition | Where it actually occurs |
|---|---|---|
| `AI_DRAFT` | The model produced a draft; a human performed **substantive** reconstruction — fixing syntax, type mismatches, tactic errors, and logical gaps. | **The overwhelming majority of current AI formalization projects** (Ghys, OAI manuscripts, …) fall here. This is the honest label for "AI wrote a first version, a human made it work". |
| `AI_LEMMA_SUGGEST` | The model only retrieved/suggested a lemma name or proof sketch; the proof code was written entirely by hand. | Literature-search assistance. |
| `HUMAN_FULL` | Written end-to-end by a human; no model generated any proof text. | Traditional formalization; human-only projects. |
| `AI_MINOR_TWEAK` | The human-completed proof was finished; the model tuned only a small number of tactic lines. | Late-stage polishing. |
| `AI_COMPLETE` | The model emitted a **fully compilable** proof in one pass; the human performed independent audit only, with **no code modification**. | **Extremely high bar.** Requires strict L3 re-audit. Any code change by the human, however small, downgrades this to `AI_MINOR_TWEAK` or `AI_DRAFT`. |

**Anti-circulation rule:** `AI_COMPLETE` MUST NOT be assigned on the basis of
"the proof compiles". Compilability is a WP-L1 property; `AI_COMPLETE` is a
**production-history** claim — which is why it is pinned by evidence, not by
assertion: the entry is an auditor-signed attestation that the generated
draft hash equals the final proof hash (§4.2 makes the two comparable
byte-for-byte). Assigning it without a `zero_edit_attestation` entry is a
`PROVENANCE_UNVERIFIABLE` finding; the gate verdict is `BLOCK_宣称不可证`.

### 5.3 `stage`

| Value | Meaning |
|---|---|
| `draft` | First machine- or human-produced version of the proof text. |
| `refactor` | Substantive restructure (type repair, tactic rewrite, gap filling). |
| `final_tweak` | Final cosmetic or tactical adjustment before audit lock. |

### 5.4 `execution_environment` (added schema v1.1)

The chain-of-thought an auditor sees is a **surface narrative after coordinate
transformation**: the same model family produces structurally different
generating conditions on the producer's own cluster versus through an external
API — server-side context truncation, sampling caps, key-cache hits, batch scheduling, and the metering regime itself are all rewritten by
the serving side. `model_family` alone therefore does **not** guarantee that
two artifacts are comparable; this enum records the comparison axis that was
missing.

| Value | Meaning |
|---|---|
| `internal_cluster` | Self-owned cluster execution: weights deployed locally; no external billing counterparty; metering is tenable. |
| `external_api` | External API call: the server may truncate context, cap sampling, and meter on its own terms — the **sandboxed/shipped-down version** of the same model. `model_signature` MUST point at the endpoint/service-version identifier + provider release digest, NOT at the open-weight checkpoint (signing "weight identity" for an API-mediated artifact is the first form of environment confusion). |
| `local_runtime` | Local single-device inference (personal hardware, no cluster, no external API). |

**Rules:**

1. Closed enum; vague labels (云端 / 内部 / 云上某服务) are NOT values.
2. One stage = one environment. A mixed stage is FORBIDDEN — split it.
3. `execution_environment` carries **no credibility weight** (§2 applies
   unchanged): it conditions *reproducibility claims*, not truth.

### 5.5 Escape-class inventory (first draft, TP-MA008-2 #6)

The worst provenance defect is a **source lying in the anti-inflation field
itself**: a stage self-reported `HUMAN_FULL` whose proof text was actually
machine-generated (or vice versa, `AI_COMPLETE` self-reported for work that
carried heavy hidden human repair). No hash binds the label to reality —
the label is an attestation. §3.3(2) of the base spec therefore demands
that every candidate escape *class* be inventoried, with the detectable
part and the undetectable remainder stated plainly.

**Candidate detector classes (draft; each needs its own control group
before any of this is a gate):**

| # | Detector idea | What it can catch | Residual blind spot |
|---|---|---|---|
| E-1 | **Draft-hash replay** — under pinned `model_signature` + `execution_environment`, re-generate the stage and compare `statement/proof_hash` convergence (not equality) against the pinned draft | Fabricated `AI_COMPLETE` labels whose text no plausible sample from the pinned model reproduces | Sampling variance; closed-source models are un-replayable in principle; convergence statistics approach is itself unaudited statistics |
| E-2 | **Same-family fingerprint reconciliation** — cross-compare the candidate against a large corpus of same-family outputs (stylometric signals, tactic-chain shape, error spectrum) | `HUMAN_FULL` claims whose text clusters tightly with the claimed-absent model family's known outputs | Atypical writing habits dissolve the signal; a human can also deliberately imitate a family; positive-only evidence — cluster membership supports suspicion, never proof |
| E-3 | **Log/build/session timeline reconciliation** — `modification_log` timestamps vs. compiler-run logs vs. session transcripts vs. the artifact's own mtime chain | Labels contradicted by temporal evidence (e.g. a `HUMAN_FULL` stage where every recorded edit window shows machine-paced activity and none shows human editing activity) | Environments without external counterparties (local_runtime, internal_cluster) carry no third-party timestamps; session logs can be regenerated post hoc |
| E-4 | **Environment–billing reconciliation** (P9 escape vector) — `execution_environment: internal_cluster` claimed while `cost_ledger_ref` points into an external-billing slice | Standing contradictions between the environment field and the metering slice | Absent pointers (`cost_ledger_ref` optional) leave the field uncheckable; both sides are self-attested |

**Registered remainder (honest boundary, unchanged by this section):** a
determining fraud of `HUMAN_FULL` — E-1…E-4 all unexercised by the fraudster
(e.g. human transcribing model output by hand) — is **outside any reachable
technical boundary**; it is detectable only by external event witness
(§9.1 counterparty anchors) or by out-of-band human testimony. The
inventory therefore claims *coverage of falsifiable classes*, not closure
of the falsification problem. §5.2's opening claim ("to make narrative
inflation machine-detectable") must be read with this remainder attached:
machine-detectable **within the inventoried classes**; the roadmap's
positioning wording ("自报但哈希锁定") downgrades to "自报且可核查一致性"
only upon the TP-MA008-2 falsification condition actually firing, not by
appeal to this draft.

## 6. Integration schemes (two; MAY be used together)

### 6.1 Scheme A — inline source annotation

Each declaration block carries a compact provenance comment immediately above
it, in a machine-parseable marker block:

```lean
/- ProvenanceManifest:
artifact_id: GT001_step2_algIndep
artifact_type: THEOREM-COND
statement_hash_sha256: "a3f5c8d1…"
proof_hash_sha256: "7b2e9f40…"
provenance:
  - stage: draft
    model_family: InternLM2
    model_version: InternLM2-72B-Chat
    model_signature: "sha256:<checkpoint-weight-hash>"
    contribution_type: AI_DRAFT
    timestamp: "2026-10-15T17:22:00+08:00"
    auditor: Wangyi
    audit_verdict: PASS_L2
-/
theorem step2_linearIndep : … := by
  …
```

The marker is a **plain comment** (`/- … -/`), not a doc comment (`/-! … -/`),
so it does not pollute Lean's documentation namespace and does not affect
compilation. An auditor script parses all `ProvenanceManifest` blocks and
emits the master ledger.

**Integrity note (Scheme A):** because the comment lives in the same file as
the proof it describes, Scheme A alone does **not** protect against a
coordinated edit of both. Scheme A MUST be accompanied by Scheme B's
hash-locked manifest, or by the manifest's SHA-256 recorded in a separate
append-only ledger (R04).

### 6.2 Scheme B — global independent manifest

A single `provenance_manifest.yaml` at the repository root, listing every
declaration's record. This is the **authoritative** record for hash-locking
purposes:

```yaml
meta:
  manifest_version: "1.0"
  protocol: "Wangyi Protocol"
  gate: "MA-008"
  project: "lean_game_theory"
  manifest_sha256: "<self-describing hash of this file, excluding this field>"
  generated_at: "2026-10-15T18:00:00+08:00"
  generator: "ma008_provenance.py v1.0"
records:
  - artifact_id: GT001_step2_algIndep
    artifact_type: THEOREM-COND
    statement_hash_sha256: "a3f5c8d1…"
    proof_hash_sha256: "7b2e9f40…"
    provenance: […]
    modification_log: […]
```

**Self-describing hash:** `manifest_sha256` is computed over the file with the
`manifest_sha256` field set to an empty string (or omitted), so the manifest
can verify its own integrity without self-reference. Any edit to any record
changes the manifest hash — this is the tamper-evidence guarantee.

For large projects (dozens of lemmas, e.g. `lean_game_theory`), Scheme B is
the primary deliverable: it supports bulk export, reporting, and a complete
provenance report.

### 6.3 Reconciliation (mandatory when both schemes are used)

When both Scheme A and Scheme B are present, the auditor MUST reconcile them:
every inline block must have a corresponding manifest record with matching
`artifact_id`, `statement_hash_sha256`, and `proof_hash_sha256`. Mismatches
are `PROVENANCE_MISMATCH` findings. When only Scheme A is present, the
auditor synthesizes the manifest and locks it.

## 7. `modification_log` — the edit chain (append-only)

The optional-but-recommended `modification_log` records each human edit as a
separate append-only entry, forming a chain from AI draft to final proof:

| Field | Meaning |
|---|---|
| `entry_kind` | Optional; `edit` (default) or `zero_edit_attestation`. `edit` entries claim human changes; the log normally records only edits. A `zero_edit_attestation` entry is the *exception*: the attester (L3 auditor) asserts that the AI-generated draft equaled the final proof (its `proof_hash_sha256` MUST equal the record's `proof_hash_sha256`), and it is the sole evidence type P6 accepts for `AI_COMPLETE`. A log containing both an edit entry and a `zero_edit_attestation` for the same record is self-contradictory → `BLOCK_宣称不可证`. |
| `sequence` | Monotonic integer, starting at 1. |
| `proof_hash_sha256` | Hash of the proof text *after* this edit. |
| `edit_summary` | Free-text description of what was changed (e.g. "repaired type mismatch on `step2`; replaced `simp` chain with explicit `exact`"). |
| `editor` | Identity of the editor (human or agent). |
| `timestamp` | ISO 8601 with timezone. |
| `prev_hash` | Hash of the *previous* log entry (empty for sequence 1). This links entries into a chain; a broken link is `PROVENANCE_CHAIN_BROKEN`. |

This is the **append-only ledger discipline** (R02) applied to the production
history: edits are never overwritten, they are appended. The chain makes it
impossible to later claim that a proof was `AI_COMPLETE` when the log shows
three rounds of human type repair.

`modification_log` is the mechanism that turns the "AI draft → human rewrite"
distinction from a label into **evidence**.

**Log–record reconciliation (SHOULD; strict-bound pending TP-MA008-2):**
when a `modification_log` is present, its final `edit` entry's
`proof_hash_sha256` SHOULD equal the record's `proof_hash_sha256`; a
deviating log is disclosed as a warning (`PROVENANCE_STALE_LOG`) until the
reconciliation threshold is measured on real manifests
([roadmap/ROADMAP-MA-008.md](../roadmap/ROADMAP-MA-008.md) TP-MA008-2). The
same rule fixes `prev_hash`'s object of hashing: the canonical log-entry
text is the record's YAML entry serialization (key order preserved, as
serialized by the implementing tool).

**Measurement protocol for the threshold (registered 2026-10-18, item open):**
closing this to strict requires ALL of: (i) ≥ 2 real manifests with
non-empty `modification_log` sections (the current production corpus has
none — every real manifest to date has an empty log, so the warn channel
has fired zero times and no rate is estimable yet); (ii) for each, the
`PROVENANCE_STALE_LOG` count and the semantically-classified cause
(trailing cosmetic edit vs. post-freeze substantive edit); (iii) an
a-priori decision rule written BEFORE observation: if any observed
deviation corresponds to a substantive post-register edit, the field
tightens to strict must-equal; if all deviations are trailing cosmetic
edits within a declared tolerance window, the rule tightens to a bounded
tolerance instead (window size taken from the observed set, rounded down
to the strictest defensible bound). Observing first and writing the rule
afterwards is the same failure the value-freeze discipline forbids.

## 8. MA-008 gate rules

### 8.1 Preconditions

MA-008 applies to any formal artifact containing **one or more** declarations
at `theorem`/`lemma`/`axiom` position. Single-declaration artifacts MAY use
Scheme A only.

**Single-vs-multi asymmetry (normative boundary, added TP-MA008-2 #8):**
the verdict set treats these two cases asymmetrically **by design**, not as
an inconsistency:

| Situation | Verdict | Why |
|---|---|---|
| Single-declaration artifact, record missing | `BLOCK_溯源清单缺失` (P1 fail) | The auditor can enumerate the missing object exhaustively — exactly one declaration, exactly zero records. The defect is fully known, so a definitive BLOCK is adjudicable. |
| Multi-declaration artifact, manifest absent | `INCONCLUSIVE` | Record count cannot be computed at all (P1's comparison has one side undefined); the defect set is unknown and possibly unboundable, so adjudication is refused rather than guessed. |

A multi-declaration artifact with a manifest that covers fewer declarations
than exist is *not* the same case: that is a stale or incomplete manifest and
goes through the P1 reconciliation path (block on concrete missing records;
the aggregate-disclosable part is emitted as findings, see TP-MA008-2 #2
draft rule).

### 8.2 Checks

| Check | Id | Type | Pass criterion |
|---|---|---|---|
| Every declaration has a record | `P1` | strict | Count of provenance records = count of declarations in the GAP ledger. |
| Per-declaration granularity | `P2` | strict | No project-level blanket provenance statement stands alone. **Machine-operator draft (TP-MA008-2 #9, non-normative organizer)**: fire candidate when (i) a declaration inventory exists and (ii) the per-declaration record set is absent (or one blanket statement covers all) and (iii) project-README/report prose matches a blanket pattern (e.g. "produced with AI assistance", "AI 辅助完成", "project was written with model X"). The operator is a *lead generator for the human auditor*, not a decision procedure: regex-level prose matching both over- and under-covers, so until it survives a four-axis control group the P2 adjudication stays a human-auditor call with the operator output attached as evidence. Honest status: the pass criterion above remains the normative rule; this paragraph adds no enforcement. |
| Required fields present & non-empty | `P3` | strict | All §4 required fields present; `contribution_type` is a valid enum value. |
| Hash reconciliation | `P4` | strict | `statement_hash_sha256` / `proof_hash_sha256` match the source (Scheme A) or manifest (Scheme B). |
| Enum validity | `P5` | strict | `artifact_type`, `contribution_type`, `stage` all in normative enumerations. |
| `AI_COMPLETE` substantiation | `P6` | strict | `AI_COMPLETE` requires a `modification_log` entry with `entry_kind: zero_edit_attestation` whose `proof_hash_sha256` equals the record's own `proof_hash_sha256` (draft = final, so the record itself is the binding evidence that the generated proof was never edited), signed by the auditor, plus L3 re-audit. |
| Manifest hash lock | `P7` | strict | Scheme B manifest's `manifest_sha256` verifies; manifest is append-only. |
| GAP-skeleton registration | `P8` | strict | Every `GAP-SKELETON` record has a matching GAP ledger entry. |
| Execution-environment registration & signature coherence | `P9` | **warn (suspended)** | manifest_version ≥ 1.1: every stage carries `execution_environment`; absences disclosed per item, never silently defaulted (reverse burden of proof); no environment mixing within one stage; signature semantics follow the environment (weight hash vs endpoint identifier). Promotion to strict pending [roadmap/ROADMAP-MA-008.md](../roadmap/ROADMAP-MA-008.md) TP-MA008-1. |

### 8.3 Verdict table

| Result | Verdict |
|---|---|
| All checks P1–P8 PASS | `PROVENANCE_VERIFIED` |
| `P1` fails (missing records) | `BLOCK_溯源清单缺失` |
| `P2` fails (project-level blanket only) | `BLOCK_粒度不足` |
| `P3`/`P5` fails (invalid/missing fields) | `BLOCK_字段不合规` |
| `P4` fails (hash mismatch) | `BLOCK_哈希不匹配` |
| `P6` fails (`AI_COMPLETE` unsubstantiated) | `BLOCK_宣称不可证` |
| `P7` fails (manifest hash broken) | `BLOCK_哈希锁失效` |
| `P8` fails (unregistered skeleton) | `BLOCK_缺口未登记` |
| Manifest absent on a multi-declaration project | `INCONCLUSIVE` (MA-008 default: missing provenance ledger → cannot adjudicate) |

**P9 transition semantics (warn-only):** while P9 is suspended, it emits
per-item disclosures and gate warnings but produces **no verdict and no new
closed-set value** — a manifest with P9 warnings alone still resolves to its
P1–P8 verdict. The closed verdict set (§10 schema) is therefore unchanged by
v1.1. Promotion to `strict` is tracked by
[roadmap/ROADMAP-MA-008.md](../roadmap/ROADMAP-MA-008.md) TP-MA008-1 and
requires the T01-style four-axis test group (positive / negative / boundary /
escape) to pass on P9 plus one round of real-manifest field exposure.

**Default-on-missing:** a multi-declaration project that ships no provenance
ledger is `INCONCLUSIVE`, not `PASS`. This is the reverse-burden-of-proof gate
(§1.3 of spec) applied to provenance: absence of evidence is not evidence of
honest production.

### 8.4 Interaction with MA-007

MA-008 is **independent** of MA-007 and composes with it. A project can be:

- `MATHLIB_VERIFIED_COMPLETE` + `PROVENANCE_VERIFIED` — fully audited on both
  the mathematical and the production axes;
- `MATHLIB_VERIFIED_COMPLETE` + `BLOCK_粒度不足` — mathematically clean but
  its production narrative is unauditable (this is the Ghys/OAI profile);
- `INCONCLUSIVE` (MA-007 condition B) + `PROVENANCE_VERIFIED` — the math is
  unverifiable externally, but the production chain is honestly recorded.

A combined verdict is reported as a pair, e.g.
`MATHLIB_VERIFIED_COMPLETE / PROVENANCE_VERIFIED`. Neither axis may be
inferred from the other.

## 9. Relation to the compute-chain route (two distinct ledgers)

Two separate ledger families exist in the SiliconLifeOS research tree, and
they MUST NOT be conflated. Both borrow cryptographic hashing, immutability,
and chained storage — but they ledger **different objects** for **different
consensus goals**:

| Dimension | Compute-chain (Feb 2026 route) | Provenance chain (MA-008) |
|---|---|---|
| **Ledger object** | Compute shards, task assignments, node resource contributions | Single lemmas/theorems: proposition text, proof code, model version, contribution type, audit verdict |
| **Core hashes** | Task-package hashes, node compute-submission digests | `statement_hash`, `proof_hash`, manifest SHA-256 lock |
| **Consensus goal** | Prove a node *executed* computation; allocate compute credits | **Freeze the production chain** of a proof; distinguish AI draft / human rewrite / pure-human |
| **Tamper protection** | Prevent nodes from faking compute or claiming others' tasks | Prevent post-publication rewriting of a proof's origin — e.g. recasting "AI draft + heavy human repair" as "AI independently proved the conjecture" |
| **Truth judgement** | Does **not** validate mathematical truth; only compute delivery | Does **not** generate truth; provenance records are *bound to* the WP-L1/L2/L3 verdicts — two ledgers, one audit |
| **Character** | A **compute** work-proofs chain (mining-class) | A **knowledge-provenance** chain (spectral-evidence class) |

**MA-008 is not a mining chain.** It does not compete for compute rewards.
It is the application of cryptographic evidence to the **genealogy of
formal mathematical artifacts**: its sole purpose is to freeze the production
chain of a knowledge artifact and prevent narrative tampering.

**Integration (optional, recommended):** the two chains interoperate. The
compute chain schedules and records the distributed Agent clusters that
*search for and generate* Lean drafts; the provenance chain receives each
produced artifact, hashes and labels it per declaration, and feeds it into
L3 audit. The compute chain handles **production scheduling**; the provenance
chain handles **output provenance and audit storage**. Together they form a
closed loop: *who computed what* (compute chain) → *what was produced and by
which model* (provenance chain) → *whether it is true* (WP-L1/L2/L3).

### 9.1 Cost ledger pointer & the asymmetric-environment problem (added v1.1)

**The engineering fact beneath the surface narrative.** Chain-of-thought
output seen by an auditor is a surface narrative after coordinate
transformation; underneath it sit two materially different generating
environments that are **not equal**:

- on the producer's **internal cluster**, execution can bypass the token
  metering regime that external API consumers are subject to — unlimited
  context, uncapped sampling, free resampling, full cache visibility;
- the **external consumer** receives a sandboxed, isolated, metered version
  of the same model family: context truncation, sampling caps, opaque cache
  behavior, provider-side batching.

The compute/token **cost of producing an artifact is itself provenance**.
Publishing results without recording under which regime they were generated
is *environment confusion* in results marketing.

**Discipline — the split:** environment class and cost figures are audited
differently, so they ledger differently:

| Object | Where it lives | Why |
|---|---|---|
| `execution_environment` (closed enum) | provenance manifest, per stage | It is a **structural, auditable fact** about reproducibility — conditions of generation, not a price tag. |
| `cost_ledger_ref` (hash pointer) | provenance manifest, per stage | Pointer only. The pointed-to slice must satisfy the triple registration below (defined normatively in this repository, no external reference needed). |
| token consumption, cache policy, quotas, wall-clock | **compute-chain billing ledger** (append-only; provider bills serve as third-party anchors where available) | These are **self-attested quantities**: internal-cluster metering has no external counterparty to audit it. Copying self-attested numbers into the provenance manifest would convert an auditable gate into an unauditable marketing annex. |

**Triple registration for the pointed-to slice (normative, self-contained).
** A `cost_ledger_ref` pointer is valid only if the billing-ledger slice it
points into carries all three parts:

1. **Pointer** — the slice's SHA-256, equal to the value stored in
   `cost_ledger_ref` (64 hex). The slice is identified by this hash, not by
   a mutable name.
2. **Scope statement** — the slice declares which metering regime its
   figures come from: third-party-anchored (provider bills exist as
   external counterparty anchors) or self-attested (internal-cluster
   metering has no external counterparty to audit it). The scope label
   travels *with* the numbers, so a consumer reading the slice sees the
   reliability class without consulting the manifest (§2 applies: no scope
   label upgrades any truth grade).
3. **Conflict rule** — when two slices both claim coverage of the same
   stage, the first-registered slice is authoritative; the dispute is
   appended as a new slice entry (R02), never resolved by editing history.

The provenance manifest carries **none** of these numbers, only the pointer
— the manifest stays auditable while the self-attested quantities live in
the ledger whose slice honestly labels their own reliability.

The two chains close the loop with cost included: *who computed what, at what
measured cost* (compute chain) → *produced under which serving regime* (P9 +
`execution_environment`) → *what the artifact is and by which model*
(per-declaration provenance) → *whether it is true* (WP-L1/L2/L3).

`cost_ledger_ref` itself carries **no credibility weight** (§2): a
"we spent N GPU-hours" figure does not upgrade any truth grade, and an
absent pointer is not a block until P9 promotes to strict (then only the
pointer-presence warning escalates; the *amounts* always stay in the
compute-chain ledger).

**One-line positioning for the protocol:**

> *The knowledge-provenance ledger is cryptographic evidence applied to the
> genealogy of formal mathematical artifacts. Distinct from a compute
> work-proofs blockchain, it competes for no compute reward; its sole purpose
> is to freeze the production chain of a knowledge artifact and prevent
> tampering with the narrative of results.*

## 10. Normative schema

The machine-readable schema is
[../schema/provenance_schema.yaml](../schema/provenance_schema.yaml), which
fixes: the field set and types, the four closed enumerations (`artifact_type`,
`contribution_type`, `stage`, `execution_environment`), the closed verdict
set, the record fields, the manifest self-hash convention, and the P1–P9
check set (P9 warn-only until TP-MA008-1 closes). Audit scripts MUST validate
against it; a provenance record that does not parse against the schema is a
`PROVENANCE_UNPARSABLE` BLOCK.

Schema v1.3 additionally carries three **draft-shape sections** (TP-MA008-2
batch 2; additive, nothing in P1–P9 or the verdict set changes):
`audit_verdict_enum` (first-draft disclosure set for the per-stage
`audit_verdict` field; P3 does not enforce it), `provenance_verdict_record_fields`
(the optional published shape of an MA-008 adjudication record), and
`gap_ledger_entry_fields` (the reconciliation-anchor shape a GAP ledger
entry must parse to, giving P8 a concrete key: `gap_id ↔ GAP-SKELETON
record's artifact_id`). The manifest meta also gains `schema_version` —
distinct from, and not to be conflated with, the manifest lineage field
`manifest_version`; P9(a) dispatch reads `schema_version` when present and
falls back to `manifest_version` for legacy v1.0/v1.1 manifests.
